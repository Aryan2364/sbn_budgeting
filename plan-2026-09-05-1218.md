## 2. PRODUCT

Tree plantation tracking for Sadbhavna.

A donor funds a **project** for a number of trees. The project is
delivered across one or more **sites**. Each site has its own tree count,
location, manager and supervisor. Each site carries a **per-tree budget**
split across **cost heads and across five periods**; the head-period
budget is the per-tree amount times the site's tree count. **Expenses**
are booked against a site and a head. The headline output is a
**site-wise, head-wise budget versus actual variance report**.

Stack: **Next.js** frontend (this repository), **NestJS** API,
**PostgreSQL**. The API does not exist yet — it arrives in Phase 3.

Brand colour is bottle green `#174443`. It lives in `app/globals.css` and
nowhere else.

`Sadbhvana Budget Tracker.xlsx`, three sheets: **Budget**, **Expense**,

everything in sections 3 to 5 that is new comes from reading it.

## 3. LOCKED DECISIONS

Do not reopen these. Do not ask about them. They are settled.

**Responsive.** Desktop and tablet only, per AGENTS.md §9 exactly as
written. Check every screen at **1280, 1024 and 768** pixels. Below 768
the layout must not break, overlap or push content off screen, but it is
not designed for. **Do not build phone screens. Do not amend §9.**

**Money.** Store as **bigint paise**. Never a float, never a decimal
type, never rupees. Format only at the display layer, through
`lib/format.ts` (built in Phase 2). A number that reaches a screen
unformatted is a bug.

**Five budget periods, fixed by the sheet.** Initial, Year 1, Year 2,
Year 3, Year 4. Stored as a `smallint` 0 to 4 rather than a Postgres enum
or a lookup table: the ordering is what the report needs and comes free,
there is nothing to join, and if a project ever runs to a sixth year that
is a data change rather than a migration. The labels live in one place in
the client.

**Cost heads are a fixed list of 19**, seeded from section 2.1. The
free-typing that stood in for this is removed.

**Seed the head names exactly as the sheet spells them, including
`Miscellenous`.** It is misspelled. It is not this plan's to correct: it
is what the people using the sheet read and type today, and silently
renaming a master while importing their data is how an import stops
reconciling. **If it should be `Miscellaneous`, that is a question for the
user, asked before the seed runs, not a fix applied on the way past.**
Whitespace is the one exception, per section 2.1.

**Variance maths.**
```
head-period budget = per_tree_paise × site.planned_trees
head budget        = sum of that head's five period budgets
site budget        = sum of every head-period budget for the site
actual             = sum of expenses booked to that head
variance           = budget − actual
```
Computed **in SQL**. Never in the client. Whether `actual` can also be
cut by period is settled: every expense stores its own period (see below).

**Tree count changes recompute budgets live.** There is no snapshot.
Because of that, **every budget figure on screen states its basis**, for
example `₹40.00 per tree × 5,000 trees, Year 1`. A budget number with no
basis beside it is incomplete, and with five periods the basis now has to
name the period as well.

**Variance query shape.** One row per `(site, cost head, period)`
carrying `budget_paise` and `actual_paise`, rolled up to head totals and
to site totals **in the same SQL definition**. Not two queries, and now
not three. Separate queries let the site totals, the head rows and the
period columns drift apart.

**Report shape.** A site list first (AGENTS.md §11.1 list page). Each row
drills into that site's head-wise **Variance tab** on the site detail
page (§11.2). Default sort is **variance ascending**, so the most
overspent sites are on screen without anyone filtering. Sort survives
page changes. **The project-wide cross-tab is out of scope.**

**Confirmed by the spreadsheet.** The Expense Summary sheet is that
second screen already: one site, cost head against sum of amount, grand
total at the bottom. The shape was agreed before the file arrived and the
file agrees with it. What the sheet does not have — the budget column,
the variance column, and the five periods — is what this product adds.

**Zero budget, at both site and head level.** Where **no budget rows
exist**:
- The Budget cell reads `Budget not set` in `text-secondary`.
- A site or head budgeted deliberately at zero shows `0.00`. These two
  states must look different.
- Variance and Variance % render an em-dash `—`.
- No badge. No danger colour. Missing data is not overspend.
- `NULLS LAST` explicitly, in **both** sort directions. Postgres defaults
  to NULLS LAST on ASC but NULLS FIRST on DESC, so descending would float
  them back to the top.
- A site with some heads budgeted and one head carrying unbudgeted spend
  is **not** this case. It has a real total and a real overspend.

**This ruling is exercised by real data on day one and it holds
unchanged.** **Irrigation is budgeted at zero across all five periods**,
and **Rajkot has an Irrigation expense of ₹3,178**. Rajkot has other
heads budgeted, so by the last clause above this is a real overspend on a
real total, not a missing-data case: it shows a budget, an actual and a
variance, with the danger colour and the word "over". Nothing about the
rule changes. Which of the two zero states Irrigation lands in — a
deliberate `0.00` or `Budget not set` — is settled below: blank is `Budget not set`.

**Variance direction.** Every variance carries an explicit **"over"** or
**"under"** word in the row. Never colour alone (§7.2 rule 1). Use the
danger colour **only** where a site or head is genuinely over budget. A
site at 40 percent spend is not a problem and must not be styled as one.
Percentages to one decimal.

**`--radius-tick` is 4px and is used on tick boxes only.** Recorded in
AGENTS.md §5.3 as a third permitted radius. A 16px square at the 8px
control radius reads as a radio button.

**One `--backdrop` token**, derived from `--text-primary`. `dialog.tsx`,
`alert-dialog.tsx` and `sheet.tsx` all point at it. None defines its own
overlay. Recorded in AGENTS.md §24.

**The seven brand tokens are explicit values, edited together.** They are
not derived from `--primary`: hover goes lighter for a dark brand and
darker for a light one, and no formula flips that. §2.1 asks for the
change to happen in one *place* — the brand block in `globals.css` — not
on one line. **The swap test passes when nothing OTHER than the five
derived shades holds the old colour.**

**Settings card Save buttons are primary.** §6.1 rule 1 and §11.5
conflict and the more specific rule wins. Recorded in **AGENTS.md §11.5**
with the reasoning; that is where it lives, not here.

### Answered 5 Sep 2026 — added to this section

Every question in section 4 is now closed. The rulings follow; section 4
keeps the question each one answers.

**Auth: office staff log in. Managers and supervisors are people records
that may or may not have a login.** `users` carries `role`, one of
`admin` or `staff`, and a nullable `password_hash` beside a `can_login`
flag. A person who only appears on a site record has `can_login = false`
and no password.

**There is no roles table and no role_permissions grid.** The
conditional block that carried that design is removed from section 5.
Do not build it. AGENTS.md §26 still governs what is hidden and what is
disabled, but there are exactly two roles to enforce: **admin sees
Settings and can delete; staff does not and cannot.**

**`sites.manager_id` and `sites.supervisor_id` are foreign keys to
`users`.** There is no separate people master and no `types` array — any
user may be named on a site, whether or not they log in.

**Every expense stores its period explicitly. It is never derived at read
time.** `sites` carries a required `plantation_start_date`; `expenses`
carries a required `period`, a `smallint` 0 to 4 on the same encoding as
`site_budgets`. The form pre-fills the period by deriving it from the
expense date against the site's start date, and the user can override it
from a dropdown.

The reason is worth keeping, because "just derive it" will look cleaner
to whoever reads this next: **a late-booked invoice or a corrected start
date would silently reclassify historical expenses and change a report
somebody has already read.** Derivation is a convenience at entry. The
stored value is the record.

**Blank budget cells are permitted, and blank is not zero.** The Phase 5
grid shows all 95 cells. An **empty** cell writes no `site_budgets` row
and reads `Budget not set`. A cell holding an **explicit 0** writes a row
with `per_tree_paise = 0` and reads `0.00`. The two must look different,
per the zero-budget ruling above. This is what decides Irrigation: it is
blank in all five periods, so it reads `Budget not set`, and Rajkot's
₹3,178 against it is spend on an unbudgeted head.

**Site tree counts against the project: a soft warning, never a block.**
Saving a site whose trees push the site total above the project's
`planned_trees` is allowed, and shows a warning. Project detail displays
the allocation — `4,000 of 5,000 trees allocated across 3 sites`.

**No receipt attachments in v1.** No upload control anywhere, per
AGENTS.md §29. The bill / voucher number is the paper trail.

**Period filtering on the variance report.** The Reports landing list
stays **all-time, with no filter of any kind**. The site detail Variance
tab gains a **period selector** defaulting to `All periods`, with
Initial and Year 1 to Year 4 as the other options. Rows stay one per cost
head and **the table stays five columns**.

**Do not build a budget / actual / variance triple per period.** Fifteen
columns would force horizontal scroll, which AGENTS.md §10 calls a last
resort. The selector changes which period the five columns are showing,
not how many columns there are.

**`Miscellenous` is seeded exactly as the spreadsheet spells it**, and
that is now final rather than pending. `cost_heads` is master data,
editable in Settings, so a correction is a row edit rather than a
migration. The six trailing spaces stay trimmed (section 2.1).

### Known constraints — not bugs, and not to be re-raised as bugs

#### The Expenses tab badge is UNPROVEN, and the check that "passed" proves nothing

**Do not record this as verified, and do not re-run the same check and
call it done.**

The fix: the Expenses tab badge on the site detail page reads the API's
`total` rather than the length of the page it fetched. Before it, a
site with 200 expenses showed a badge reading **25** — a wrong number
with nothing on screen to contradict it.

**Why the production check was worthless.** The largest site has **21
expenses** and the page size is **25**. Below the page size the page
length and the true total are *the same number*, so the badge reads 21
either way. It read 21, which is correct — and would have read 21
under the old code too. **A check that cannot fail is not a check**; it
measured agreement between two values that cannot disagree in that
range.

**What would actually prove it**, any one of these:

- A site with **more than 25 expenses**. The badge must show the true
  count while the table shows 25 rows and the pagination bar appears.
  The discriminating observation is badge ≠ rows rendered.
- Temporarily lowering the page size below the row count — set
  `EXPENSES_PAGE_SIZE` to 5 against the 21-expense site. Badge must read
  21, table 5 rows, four pages. Cheapest option and needs no data.
- The same shape on the Settings masters: 21 cost heads against a page
  size of 25 has the identical problem, so lower the size there too
  rather than waiting for a 26th cost head.

**The general form, worth carrying beyond this item:** a fix to a
truncation bug can only be demonstrated on data that actually
truncates. Verifying it below the threshold measures nothing and reads
in a report exactly like verifying it above one.

#### `SearchableSelect` loads a fixed 100 options and filters in the browser

**The control choice is correct and is not the issue.** Section 16.3
says a list past twenty options should be a searchable picker rather
than a dropdown, and every place that needs one already uses
`SearchableSelect`. The plain `select` that remains in `expense-form`
is the five-option period picker, which is what `select` is for.

**The limit is behind the control.** `SearchableSelect` filters a
client-side `options` map, and **every caller fetches a fixed
`pageSize: 100`** — projects and sites in `report-scope`, projects,
locations and people in `site-form`, sites and cost heads in
`expense-form`. So:

> **A master with more than 100 rows silently loses every option past
> the hundredth.** The picker's search box searches only what was
> fetched, so an option that exists in the database simply cannot be
> found, and nothing on screen says the list is partial.

**Current counts: 21 cost heads, 3 people, 2 projects, 2 sites.**
Nowhere near it, and these are masters that grow by admin edits rather
than by use, so the threshold is years away at the present rate. It is
recorded because the failure is silent, not because it is close.

**Fixing it is scoped work, not an audit fix.** It means adding an
async mode to `SearchableSelect` — debounced server-side search, or
paging as the list scrolls — and rewiring **five call sites** to match.
That is a component redesign with its own testing, and doing it inside
an audit pass is how an audit turns into a rewrite.

**The tripwire, if anyone wants one:** the API already returns `total`
on every list response, and every one of these callers throws it away.
Comparing `total` against the fetched length would let the picker say
"showing 100 of 137" rather than lying by omission. That is a much
smaller change than async search and would close the *silent* part of
the failure without touching the control.

## 7. LEARNED IN PHASES 1 AND 2

Do not rediscover these.

Items marked **(kit-relevant)** are not specific to this product. They
belong in the starter kit's own `AGENTS.md` when the kit is extracted,
because plan files do not travel between products and the next product
would hit them again from cold.

**`--chart-1` held a second copy of the brand hex.** Chart position 1 *is*
the brand colour (§21), so it must read `var(--primary)`. A literal copy
means a brand change leaves the first chart series behind.

**Forced-state CSS must sit outside `@layer` entirely.** Inside `@layer
components`, Tailwind's `utilities` layer comes later in the cascade and
overrode it — the kitchen sink state matrix silently rendered the resting
colour in the hover, pressed and focus columns while looking fine.
Unlayered CSS beats every layer.

**Do not borrow `Button` for grid cells.** `ghost` carries a fill and a
border to satisfy §6.1 rule 4, which is right for a button and turned
every calendar day cell grey. A day cell gets its own element and §20.1's
own states.

**Base UI puts the scroll container on `Select.List`, not
`Select.Popup`.** §16.2's seven-row scroll cap depends on it being in the
right place.

**cmdk owns `aria-selected` and renders its own tick** keyed to
`data-checked`. Use `data-chosen` for "this is the current value" and do
not add a second `CheckIcon`.

**Base UI popovers never server-render** — `keepMounted` defaults to
false. Content inside one needs no hydration deferral. A hydration
mismatch from a popover's contents means something is rendering it
inline.

**`tailwind-merge` must be told about custom token names. (kit-relevant)**
It treats any unrecognised `text-*` class as a colour, so
`cn("text-label", "text-text-secondary")` silently dropped the font size
and every label rendered at the inherited 14px. `lib/utils.ts` extends
it. **Anything added to the type scale in `globals.css` must be added
there too.**

**Do not name a type-scale token the same as a colour token. (kit-relevant)**
`--text-card` collided with `--color-card` and Tailwind resolved
`text-card` to the colour — card titles rendered white on white. It is
`--text-card-heading`.

**When measuring in the browser, scope every query by id.** The kitchen
sink has eight selects. An unscoped `document.querySelector` returned a
component that was never touched and produced a false defect report that
cost a whole session.

**Browser testing needs the window in the foreground.** If
`document.visibilityState` is `"hidden"`, dispatched keys do not behave
as they would for a user and every keyboard result is worthless. **Check
`visibilityState` before trusting any interaction test.**

**Reporting: quote line numbers and grep counts. Never paste large file
excerpts.** Long pastes truncate in transit and get reviewed as corrupt.

### From Phase 2

**A constant imported from a `"use client"` module reaches a server
component as a client reference, not as its value. (kit-relevant)** The
root layout's sidebar-restore script rendered
`localStorage.getItem(undefined)` and the saved choice silently never
came back. The key lives in `components/shell/sidebar-storage.ts`, which
is deliberately not a client module.

**`next/script` with `strategy="beforeInteractive"` is the wrong tool for
a pre-paint restore. (kit-relevant)** It only queues the code for the
client runtime, which runs after paint — that is a flash, not a restore.
A raw `<script>` in `<head>` executes synchronously and draws no React
warning; the same raw script in `<body>` does draw one.

**`Skeleton` renders a block-level `<span>`, not a `<div>`.
(kit-relevant)** A skeleton stands in for text that has not arrived, so
it has to be legal wherever that text was going to sit — inside a
heading, a paragraph, a label. A `<div>` in any of those is invalid
nesting and breaks hydration.

**Base UI throws `MenuGroupContext is missing` if `Menu.GroupLabel` is
not inside a `Menu.Group`.** It only fires when the menu opens, so it
survives any amount of code reading. It had sat latent in
`/kitchen-sink` since Phase 1.

**Derived state belongs in render, not in an effect. (kit-relevant)**
`date-picker` and `time-picker` both held text derived from a `value`
prop and resynced it in an effect, which renders the stale text once and
then immediately renders again — `react-hooks/set-state-in-effect`. They
adjust during render now, comparing on the **formatted** value rather
than the object, because a parent building a fresh `Date` every render
changes identity without changing meaning.

**`toFixed` rounds the binary value, not the decimal one.
(kit-relevant)** `(12.35).toFixed(1)` is `"12.3"`, because 12.35 is held
as 12.3499999999999996. Correct arithmetic, and the wrong answer to hand
somebody checking a percentage against a calculator. `formatPercent`
rounds half-up on the decimal, on the magnitude, so an overspend and an
underspend of the same size round the same way.

**Browser testing needs a window you can resize.** A background tab in a
maximized window will not relayout — `window.innerWidth` stays pinned at
whatever it last was, however the window is resized, and every
breakpoint result is a lie. Check `innerWidth` after resizing and before
trusting anything. A same-origin **iframe sized to the exact width**
evaluates media queries and `matchMedia` against its own viewport and is
a reliable substitute when the window will not cooperate.

**AGENTS.md now carries two things Phase 2 added:** a §23.2 shell and
navigation icon map, and the §11.5 ruling that settings card Saves are
primary.

### From the Phase 8 audit, 14 Sep 2026

**A state matrix can only verify what it forces. (kit-relevant)** A
component absent from the forcing rules renders its RESTING appearance
in the "hover" column and looks verified while being unverified — and
nothing about the page says so, because a resting control in a hover
column looks exactly like a control that has no hover.

The forcing rules in `globals.css` covered six slots. `checkbox`,
`radio-group-item` and `switch` were three of them and **had no
`hover:` or `active:` classes at all** — two of section 6.4's four
states simply absent from the three form controls a data entry user
touches most. They had sat that way since Phase 1 and every review of
the kitchen sink had passed them.

**The same mechanism fails in the other direction, which is worse.**
`input` and `select-trigger` were forced here while having no hover
styles of their own, so the matrix *displayed a state the component
could not produce for a real user*. The check did not merely miss
evidence, it manufactured it. `textarea` had neither the styles nor the
forcing, so it was invisible twice over.

**The fix that generalises is not "cover more components" — it is to
make the matrix check itself.** `components/ui/state-matrix-check.tsx`
runs in development on `/kitchen-sink`, compares every interactive
control inside a `[data-force]` cell against its resting twin, and
renders a danger panel naming anything that renders identically.
Silence is the pass. Coverage becomes self-maintaining: a component
added to the matrix without forcing rules, or a component whose states
get deleted, both surface immediately.

Two details it cost a round to learn:

- **Restrict it to elements a person can interact with.** The first run
  reported fifteen failures, every one an inner decorative part — a
  tick glyph, a switch knob, the text span inside a select trigger.
  Those inherit the control's states and should not have their own.
  Noise is how a check stops being read, which is how the matrix
  stopped being trusted in the first place.
- **Prove it fails.** The switch's hover and pressed were temporarily
  deleted, the panel named exactly `switch — "hover"` and
  `switch — "pressed"` and nothing else, and both were restored. A
  check that has only ever been seen passing is the same mistake as the
  Expenses badge verified below its page size.

**The general form, worth more than the specific bug: a verification
surface that is configured per-item will be incomplete, and its
incompleteness looks identical to success. Prefer one that derives its
own coverage and complains about gaps.**

### From the cold-connection hunt, 13 Sep 2026

**A promise that cannot reject cannot be rendered as an error, however
good the error state is. (kit-relevant)** This is the whole diagnosis
in one line, and it is why the fix was never going to be in the screen.

The symptom was the familiar one: a cold first request hangs for ever,
a refresh works. Three separate unbounded waits stacked up, and **every
layer defaults to waiting for ever**, so nothing anywhere in the stack
turns a stall into a failure:

- **`node-postgres` ships `connectionTimeoutMillis` unset, and both
  `statement_timeout` and `query_timeout` `false`.** A request that
  stalls while connecting does not fail — it never returns.
- **The browser's `fetch` has no timeout of its own.** A stalled
  request never settles, so every `.then` and `.catch` downstream
  simply never runs.
- **Idle TCP flows are dropped silently** by a NAT or a security group
  after a few minutes. The pool keeps handing out a socket it believes
  is open, and the first query after a quiet period goes nowhere. This
  is the *cause*; the two above are why it was invisible.

The fix is one line of thinking applied in three places: **bound every
wait, and make the cause addressable rather than only the symptom.**
`connectionTimeoutMillis`, `statement_timeout` and `query_timeout` on
the pool; `keepAlive` with a 30s initial delay to hold the flow open,
comfortably inside the usual 350s idle window; and an
`AbortSignal.timeout` on `fetch` that turns a stall into a retryable
sentence.

**Any product built this way has the same hole**, because all three
defaults are the library defaults. A screen with a perfect loading
state, a perfect failed state and a Retry button still hangs for ever
if the request underneath it cannot fail.

**Its sibling, found the same day: a failed load that renders as
loading. (kit-relevant)** `rows === null` is true both before the first
response and after a failed one, so `loading || rows === null ? <Skeleton/>` shows a skeleton for ever on failure — with the reason
computed, assigned and then discarded. `MasterSection` and
`budget-grid` both had it. **A failed state that shares a branch with
the loading state is not a state**, and section 13's three cases have
to be three branches.

## 8. WHAT A FAST MODEL WILL GET WRONG

Check yourself against this list before every commit.

- **Hardcoded colours inside vendor components.** shadcn and Base UI ship
  `bg-black/10`, `ring-foreground/10` and similar. They must all route
  through tokens.
- **Arbitrary Tailwind values** — `rounded-[4px]`, `h-[18px]`,
  `text-[0.8rem]`. Only `rounded-(--radius-tick)` and the named scale.
- **Weights 600 and 700.** Only **400 and 500** exist. If a heading is
  not standing out, **add space around it, do not add weight.**
- **Spacing off the §5 scale, especially 20px.** The scale is 4, 8, 12,
  16, 24, 32, 48. There is no space-5, space-7 or space-9. If 16 feels
  too small and 24 too big, the answer is one of those two.
- **Add and Edit built as two components.** They are **one file**.
- **A second component where a variant is required.** Extend the existing
  component.
- **A `dark:` utility.** Dark mode is forbidden until commissioned (§28).
  The `@custom-variant dark` line in `globals.css` stays — it is what
  stops the operating system's dark mode triggering an unbuilt theme.
- **Hover going darker.** This brand colour is dark, so **hover goes
  LIGHTER** (`--primary-hover`) and **pressed goes DARKER**
  (`--primary-pressed`).
- **A back arrow button.** There are **no back buttons anywhere**.
  Breadcrumbs replace them, maximum three levels.
- **A label in `text-primary`.** Labels are **always 13px, weight 400,
  `text-secondary`**. A label in `text-primary` reads as body text and
  the hierarchy collapses.
- **Buttons of varying height.** Exactly **36px** default, 32 small, 40
  large, icon-only **36×36** (§6.2). Width grows with the label; height
  never does.
- **A ghost button with no fill or border.** A button the user cannot see
  is a button is broken (§6.1 rule 4).
- **A toast for a field validation error.** Use `InlineFieldError`. The
  user cannot remember which field was wrong after a toast vanishes.
- **A native `confirm()` or `alert()`.** Always `AlertDialog`.
- **An unbounded list.** Everything is paginated, 25 rows.
- **A nested scrolling area.** Never one inside another.

### The hidden-tab trap, for the fourth time — and I got it wrong first

Measuring the chart in a backgrounded tab, the SVG stayed 1125px while
its container reported 677px at a 768px viewport. I read that as
Recharts' `ResponsiveContainer` failing to re-measure, replaced it, and
wrote a confident comment saying so.

**It was the tab.** A direct test — attaching a `ResizeObserver` inside
the iframe and resizing it — returns **zero callbacks, not even the
initial one**. Chrome delivers `ResizeObserver` callbacks during the
rendering steps, and a tab that is not being painted does not run them.
`ResponsiveContainer` uses a `ResizeObserver`; so does anything else
that measures. The observation was worthless and the conclusion was
wrong.

The comment in `bar-chart.tsx` now says what was actually established.
The replacement stays, for a reason that survives the correction and is
better than the one I first gave: **the first measurement is a direct
`getBoundingClientRect()` on mount and does not wait for the observer
to fire.** That is why the mount path verifies cleanly at all four
widths in a hidden tab, where an observer-only chart cannot. Live
resizing is **unverified** and is on the Phase 8 list.

Earlier entries flagged this trap three times, for hover and for window
resizing. It applies to **anything driven by the rendering steps**, and
a measurement is one of those. That is the general form, and it is the
version worth remembering.

### A real finding: `deploy.sh` can leave the backend stale

**The backend `:latest` tag moved and the container was not
recreated.** Measured, in the same ID space so the comparison is valid:

| | tag `.Id` now | container is running |
|---|---|---|
| frontend | `31a5c2f…` | `31a5c2f…` — **matches** |
| backend | `2de78c2…` | `d016075…` — **STALE** |

`compose pull` fetched a newly built backend image, `compose up -d`
said `Running`, and the container kept the old one.

**It is harmless this time and that is the only reason it is not an
incident.** No backend source changed, so `2de78c2` is a rebuild of
byte-identical code and `d016075` runs the same application. Checked:
`/api/reports/variance`, `/periods-summary` and `/head-periods` all
answer 401, so the backend is up and guarding.

**It will not be harmless next time.** The next commit that *does*
change backend source can pull a new image, print `Running`, and leave
production on the old code — a deploy that reports success and ships
nothing. Compose's recreate decision keys on its stored config hash,
which contains the image *reference* (`…:latest`) and not the resolved
digest, so a moved tag does not always change it.

**Not fixed here, because it is a deploy-pipeline change and this was
an audit batch.** The candidate fixes, cheapest first: add
`--pull always` to the `up` in `deploy.sh`; or `compose up -d
--force-recreate`; or pin the compose file to an image digest per
deploy rather than to `:latest`. **Whichever is chosen, the test is
the table above** — compare each tag's `.Id` against the running
container's `.Image` after a deploy, not the exit code.

### The deploy pipeline no longer exits zero on a no-op

`deploy.sh` that resolves each service's image reference and compares

`DeleteRecordDialog` rendered its `<InlineFieldError>` as a **sibling**
